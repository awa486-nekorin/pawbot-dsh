# Independent review — PawBot Minecraft guard (Fabric 1.20.1 / Java 17)

Date: 2026-11-01 (Asia/Shanghai)
Reviewer: delegated independent Fabric security/correctness specialist
Scope: `AGENTS.md`, Desktop `不可用提示詞-修改稿.txt` (v4), `minecraft-guard/**` source (excluding `.gradle`, `.tooling`, `build` caches), `app/pawbot/minecraft_guard.py`, and the Node guard contract (`app/minecraft-sidecar/src/{guard,controller,adapter,main,skills}.js`, plus the host-side resident/control/lifecycle call sites).

Constraints honoured: no implementation, test, config, or docs edits; no real game, world, private data, credentials, or deployment; only this report was written into the repository. All reproductions below used synthetic `%TEMP%` directories and the already-built classes. The existing build was **not** re-run.

## 1. Verdict

**Not ready for live use as-is.** The core design is largely sound on the paths covered by the 37 self-tests (exact signed bytes, nonce/replay, request shape, actor/target caps, world path/marker, integrated-only, LAN current-port, server-thread save before snapshot, backup freshness, link checks on copy, retention names, restore no-overwrite/source-read-only). However, this review found **six must-fix defects** outside the self-test coverage:

| ID | Severity | Status | One-line finding |
| --- | --- | --- | --- |
| F1 | **P0 / critical** | Confirmed by reproducible temp test | Recursive backup deletion follows NTFS junctions, so `cleanupTemp`/`prune` can delete arbitrary directory contents, including the owner's original world. |
| F2 | **P1 / high** | Confirmed by reproducible temp test | `revoke` returns a signed 200 even when the persistent revocation marker cannot be written; a restart re-arms the guard. |
| F3 | **P1 / high** | Confirmed by code-path analysis; live duration not measured | Any save/snapshot longer than the sidecar's 650 ms guard deadline makes the watchdog quarantine the bot; periodic backups make this recurring. |
| F4 | **P2 / medium** | Confirmed by reusable temp test | `RestoreTool` only scans 64 ancestors; a target deeper than that inside a running world is accepted and written. |
| F5 | **P2 / medium** | Confirmed by reusable temp test | The Java guard issues a `pvp` permit with `can_write=false` and `can_pvp=true`; the Node sidecar and Python policy currently stop it, but the guard's capability contract is inconsistent. |
| F6 | **P2 / medium** | Confirmed by reproducible Python test | The Python client accepts a case-different `world_path` in `GuardSettings.validate()` but rejects the guard's canonical mixed-case `save_path` in `verify_attestation()`. |

The build evidence is real but narrow: `reports/minecraft-review/guard-build.log` shows `BUILD SUCCESSFUL`, `remapJar` succeeded, and `passed=37 failed=0`. The suite is JDK-only, uses `FakeWorld`, and does not exercise `GuardMod`, `IntegratedWorldAdapter`, actual Minecraft, junctions in the deletion paths, or the Node/Python timing interaction. Passing tests are therefore **not** evidence for the findings above.

## 3. Must-fix findings

### F1 — P0 — Recursive delete follows junctions; `cleanupTemp`/`prune` can destroy arbitrary directories

**Where**
- `minecraft-guard/src/main/java/dev/pawbot/guard/BackupManager.java:142-154` — `cleanupTemp()`; the candidate test at line 148 uses `Files.isDirectory(p, LinkOption.NOFOLLOW_LINKS)`, which is `true` for an NTFS junction; line 150 calls `deleteTreeQuietly(p)`.
- `BackupManager.java:120-139` — `prune()`; line 134 calls `PathSafety.requireNoLinks(p)` on the top-level directory only; line 135 then recurses with `deleteTreeQuietly(p)`, which does not inspect descendants.
- `BackupManager.java:266-284` — `deleteTreeQuietly()`; line 268 `Files.walkFileTree(root, ...)` has no reparse-point check. On Windows a junction reports `isDirectory=true`, `isSymbolicLink=false`, `isOther=true`; `walkFileTree` descends through it.
- `minecraft-guard/src/main/java/dev/pawbot/guard/GuardMod.java:94` — `cleanupTemp()` runs on every guard start, before `PermitService` and before the listener. It is not gated by `write_enabled`, so it runs even with writes disabled.
- `minecraft-guard/src/main/java/dev/pawbot/guard/RestoreTool.java:250-268` — a duplicate `deleteTreeQuietly` with the same root-following shape (reachable on restore failure/race; lower likelihood than F1 but same fix).

**Scenario A (startup, deterministic)**
1. The configured backup root is writable by a local process, a sync/backup tool, or a shared-volume user.
2. That process creates `backups/tmp-<32 hex>` as a junction to the owner's original world (or any victim directory).
3. The owner starts the world with the guard enabled. `GuardMod.onServerStarted` calls `backups.cleanupTemp()`.
4. `cleanupTemp` sees the junction as a directory, `walkFileTree` descends, and deletes every file/subdirectory in the victim, then deletes the junction.

**Scenario B (retention, deterministic)**
1. A `backup-\d{13}-\d{3}` directory (or a directory an attacker renamed to that shape) contains a junction child pointing at a victim.
2. `BackupManager.backup()` calls `prune()` (line 115).
3. `prune` passes the top-level `requireNoLinks(p)` because `p` itself is a normal directory, then deletes the victim contents through the nested junction.

**Reproduction result (this review, temp only)**
- A junction named `tmp-0123456789abcdef0123456789abcdef` pointing at a temp `victim` caused `cleanupTemp()` to remove `victim/important.txt`, `victim/sub/nested.txt`, and the junction.
- An old backup directory containing a junction to a temp `victim` caused the next backup's prune to delete `victim/important.txt`.
- A junction **inside the world** is correctly refused by `scan()`/`copyTree()` with `"link in world"`; the defect is specifically in deletion, not snapshot creation.

**Impact**
Arbitrary file deletion with the guard process's privileges, including the owner's original world — the exact asset the guard is supposed to protect — and it can happen automatically at startup. Precondition: local write access to the backup root (shared drive, sync tool, another local process) or an accidental junction. LAN/network exposure is not sufficient by itself.

**Fix**
- In `cleanupTemp` and `prune`, reject/reparse-check **every candidate** before deletion, not only path components. For a junction, delete the link itself (or refuse and report), never descend.
- In `deleteTreeQuietly`, add a `SimpleFileVisitor` that, for `attrs.isSymbolicLink() || attrs.isOther()`, deletes the entry only and returns `SKIP_SUBTREE`; check the root's `BasicFileAttributes` with `NOFOLLOW_LINKS` first.
- Also verify the backup root itself is not a reparse point at cleanup time (`PathSafety.realPathChecked(backupRoot)` / `requireNoLinks`).
- Add a Windows junction regression (`mklink /J`) for `cleanupTemp` and for a junction nested inside an old backup; the existing `linkInWorld` and `pathSafety` tests use `Files.createSymbolicLink`, which can be skipped and does not cover junctions in delete paths.

### F2 — P1 — `revoke` can be signed as successful while the revocation marker is not durable

**Where**
- `minecraft-guard/src/main/java/dev/pawbot/guard/PermitService.java:386-404` — `revoke()`.
- `PermitService.java:388` writes the marker; `:389-391` catches `IOException` and deliberately continues; `:392-393` latches in memory and resets the session; `:403` returns a signed 200.
- `minecraft-guard/src/main/java/dev/pawbot/guard/GuardMod.java:87-90` and `PermitService.java:114-120` only observe a marker that actually exists; if it was never written, a restart is armed again.

**Scenario**
The config directory is missing, read-only, or on a full disk when the owner invokes emergency stop. `revoke` returns a verified 200 receipt; the host records `revoked=true`; no marker exists; after a process restart the guard starts normally and can issue permits again. This contradicts the README/contract claim that revocation survives restart and that only a human deleting the marker re-arms the guard.

**Reproduction result (temp only)**
`PermitService` constructed with a nonexistent config directory: `revoke` returned status 200 with a signature, `Files.exists(<dir>/pawbot-guard.revoked, NOFOLLOW)==false`, and a new `PermitService` over the same directory reported `isRevoked()==false`.

**Related F2b (P2) — revoke receipt may be unverifiable / kick not proven**
- `PermitService.java:394-404`: `port` starts at 0; if `world.onServerThread(...)` times out or the LAN is closed, the catch leaves `port=0` and still signs a 200. Python `verify_attestation` requires the response port to equal the configured port (`app/pawbot/minecraft_guard.py:126`), and Node requires `1..65535` (`app/minecraft-sidecar/src/guard.js:51`). So an otherwise-correct revoke receipt is rejected by the clients, and emergency stop can report failure even though the guard latched. The same catch also means the signed receipt does not prove the actor was kicked; an in-flight skill can continue until the host stops the sidecar. The host does stop the sidecar, so this is observability/ordering, not an end-to-end write bypass.
- Fix for F2: write the marker with `CREATE_NEW`/`NOFOLLOW_LINKS` semantics, check it after writing (and fsync if possible), and only sign a success receipt when the durable marker exists. On failure, keep the in-memory latch and return a non-signed 503 (the host will then report an incomplete stop). Fix F2b by allowing/attesting a closed-LAN `port=0` for `revoke`, or by including an explicit `actor_disconnected`/`durable` field and failing closed when the kick was not confirmed.

### F3 — P1 — Inline backup blocks all attestations; the sidecar's 650 ms guard deadline then quarantines the bot

**Where**
- `app/minecraft-sidecar/src/controller.js:50` — watchdog every 250 ms; `:51` — backup timer every 1,800,000 ms.
- `controller.js:63` — every `checkPermit()` passes a **650 ms** timeout to `guard.permit()`.
- `controller.js:114-119` — `watchGuard()` calls `checkPermit()` for the active action; any failure calls `quarantine('guard_unavailable')`.
- `controller.js:120-126` — `periodicBackup()` calls `guard.permit('backup')` (60 s default).
- `minecraft-guard/src/main/java/dev/pawbot/guard/GuardMod.java:132-157` — the **Java guard itself** runs a periodic snapshot inline on the integrated-server thread (`periodicBackupOnServerThread`).
- `minecraft-guard/src/main/java/dev/pawbot/guard/PermitService.java:333-343` — `BACKUP` and `CONNECT` call `world.saveAll()` then `BackupManager.backup(...)`; `:287` waits on the server thread.
- `minecraft-guard/src/main/java/dev/pawbot/guard/BackupManager.java:70-117` — save/scan/copy is synchronous.
- `app/pawbot/minecraft_resident.py:1564` and `:2046` — the resident also triggers `backup` before ticks/skills.

**Scenario**
A periodic snapshot (Java timer, Node timer, or Python `_backup_if_due`) starts. The integrated-server thread performs `saveAll` and the file copy. The Node watchdog fires at 250 ms intervals and issues an `observe`/`write` permit. That request queues behind the snapshot; after 650 ms `requestPermit` times out, `GuardClient.permit` throws `GuardError`, `watchGuard` catches it, and `quarantine('guard_unavailable')` closes the bot connection. A 2 GiB configured world (or a slow disk/many files) is far beyond 650 ms; this will recur every backup interval. The same happens for Python-requested backups. It is fail-closed (no unsafe write), but the advertised long-running resident is not viable on a real world.

**Related F3b (P2) — backup interval is not one contract**
- `GuardConfig.java:104-108` accepts `backup_interval_sec` from 60 to 1800; `PermitService.java:349-355` denies WRITE/PVP when the session snapshot is older than that value.
- `controller.js:51` hardcodes 1,800,000 ms; `minecraft_resident.py:1316-1319` independently allows 1–30 minutes.
- If the owner sets the Java guard to 60 s (documented as allowed), the Node sidecar backs up only every 30 min; after 60 s the watchdog's write check gets `403 backup stale`, which is treated as `GuardError`/quarantine. The guard and the sidecar must share one interval (or the guard should expose it); otherwise a valid configuration is unusable.

**Fix**
- Do not hold the integrated-server thread for the whole copy while clients must attest. At minimum, make the sidecar watchdog timeout exceed the maximum backup time and treat a timeout as retry/backoff, not as a revocation; but that delays revocation detection.
- Better: split the snapshot into a short server-thread `saveAll` plus an off-thread copy with a "snapshot in progress / writes denied, observe allowed" state, or expose a guard status that lets the sidecar pause the watchdog during a known backup and resume with a fresh session.
- Publish the new `sessionBackup` before/atomically with completion so a queued write cannot read the old session after the copy; if the future times out, do not publish.
- Make the Node/Python/Java backup interval a single source of truth; derive the sidecar timer from the guard interval or reject non-default intervals in the sidecar configuration.

### F4 — P2 — `RestoreTool` accepts a target more than 64 ancestors below a live world

**Where**
- `minecraft-guard/src/main/java/dev/pawbot/guard/RestoreTool.java:51` — `MAX_ANCESTOR_SCAN = 64`.
- `RestoreTool.java:240-248` — `rejectRunningWorldAncestor()` walks at most 64 parents and refuses only if it sees `session.lock`; if the running-world root is the 65th ancestor, it is never checked.
- The existing test `restoreRejectsLockedOrRunning` (`GuardSelfTest.java:717-748`) covers only a direct child of a running world.

**Reproduction result (temp only)**
A synthetic live world with `session.lock`, 70 nested `d` directories, and target `.../d/.../restored` was accepted. `RestoreTool.restore` returned a path inside the live world (`inside live=true`). This violates the documented "no ancestor of the target may be a live world" rule and writes into a running save.

**Impact**
The restored directory is new and does not overwrite files, but it is written inside a live world; a subsequent save/backup/scan can pick it up, and it contradicts the offline-restore safety claim. Exploitability is limited to an operator choosing a very deep path; the code should not rely on a fixed depth.

**Fix**
Walk every parent to the filesystem root (`for (Path p = start; p != null; p = p.getParent())`), checking `session.lock` at each level; or reject paths deeper than the limit instead of silently stopping. Add a regression with a running-world root more than 64 levels above the target.

### F5 — P2 — `pvp` permit is issued while `write_enabled=false`

**Where**
- `PermitService.java:266-278` — `pvp` checks `pvpEnabled` and the target allowlist, but not `writeEnabled`; `write` has its own check at `:273-275`.
- `PermitService.java:430-431` — the signed body reports `can_write = config.writeEnabled` and `can_pvp = config.pvpEnabled` independently.
- Python `app/pawbot/minecraft_guard.py:150-155` requires `can_pvp` for `pvp` but does **not** require `can_write`.
- The current Node sidecar and Python policy do require write for PvP (`app/minecraft-sidecar/src/guard.js:38` and `:53`; `app/pawbot/minecraft_policy.py:103-105`), so no end-to-end write bypass through the shipped sidecar is demonstrated.

**Reproduction result (temp only)**
With `write=false`, `pvp=true`, `CONNECT` returned 200 and `PVP` returned 200 with `"can_write":false,"can_pvp":true`.

**Impact**
The Java guard's capability contract is internally inconsistent: a consumer that trusts `can_pvp` alone (the Python verifier does) would accept PvP despite writes being disabled. The current Node gate saves this configuration, but defense-in-depth and any future alternate consumer are weakened.

**Fix**
Require `writeEnabled` for `pvp` in `handle()`/`build()`, or set `can_pvp = pvpEnabled && writeEnabled` and reject the permit when false; also reject `pvp_enabled=true, write_enabled=false` in `GuardConfig` or document it as invalid; add a test that no `pvp` permit is issued when write is off.

### F6 — P2 — Case-only world-path mismatch passes local validation but fails every attestation

**Where**
- `app/pawbot/minecraft_guard.py:70` — `GuardSettings.validate()` accepts a path when `os.path.normcase(os.path.realpath(world_path)) == _canonical_path(world_path)`; Windows case differences are normalized away.
- `app/pawbot/minecraft_guard.py:138-140` — `verify_attestation()` then requires exact string equality between the signed `save_path` and `settings.world_path`.
- `PermitService.java:412-416` — the guard signs `realRoot.toRealPath().toString()`, which uses the on-disk case.

**Reproduction result (temp only)**
An existing temp world was configured with an upper-case last component; `settings.validate()` accepted it; a correctly signed response with the canonical mixed-case path raised `guard_world_mismatch`.

**Impact**
On Windows, an owner who configures `minecraft.world_path` with a case-only difference from the Java `save_path`/actual on-disk path passes `GuardSettings.validate()` but cannot connect or write; every guard attestation is rejected. This is fail-closed (no unsafe write), but it is a real integration failure and the two validations contradict each other. The Java guard also compares paths case-insensitively (`WindowsPath.equals`), so Java accepts what Python rejects.

**Fix**
Make the contract explicit: either require the exact canonical spelling in `GuardSettings.validate()` (compare `os.path.realpath(world_path)` to `world_path` without `normcase`) or compare the response path case-insensitively only after verifying both sides are canonical and resolve to the same real path. Add a cross-language test with a case-only variant on Windows.

## 5. What this review verified as correct (source/test evidence)

- **Authoritative world identity / integrated-only / current LAN / marker** — `IntegratedWorldAdapter.java:42-67` uses `getSavePath(WorldSavePath.ROOT)`, `instanceof IntegratedServer`, `!isDedicated()`, `isRemote()` and `getServerPort()`; bytecode confirms the actual 1.20.1 Yarn semantics (`lanPort > -1`, `getServerPort()` returns `lanPort`, `openToLan` sets it after bind). `GuardMod.java:163-196` and `PermitService.java:301-328` compare the real save path, require a regular `.pawbot-test-world` (NOFOLLOW, size ≤4096, trimmed content equals `world_id`), and reject non-integrated/LAN-closed worlds. Tests: `dedicated`, `worldMismatch`, `markerChecks`, `closedLAN`, `currentPort`.
- **HMAC and response bytes** — `Hmac.java:17-44` uses HMAC-SHA256 and constant-time comparison; `PermitService.java:406-439` signs the exact UTF-8 body it returns; `PermitService.java:65-80` only carries a signature on 200. Tests: RFC 4231 vector, exact signed bytes, response fields, 5 s lifetime.
- **Request shape, nonce, actor/target caps** — `PermitService.java:28-37,199-278` enforces exact keys, 32 lowercase hex nonce, lowercase UUIDs, the configured actor, empty target for non-PvP, exact PvP allowlist, and write/PvP capability checks (except the PvP/write coupling in F5). Nonce is claimed before any decision and stays burned after denial (`NonceCache.java:31-45`). Tests: strict shape, replay, wrong actor, PvP targets, write capability, target-only-for-PvP.
- **Revocation in-memory/sticky/kick** — `PermitService.java:386-446` latches in memory, re-checks the file per authenticated request, never unlatches, and `IntegratedWorldAdapter.java:112-121` disconnects the matching player. Tests: `revoke`, `revokePersists`, `externalRevokeLatches`; the actual Minecraft kick remains live-unverified. F2 covers persistence failure; F2b covers receipt verification.
- **Backup snapshot mechanics** — `BackupManager.java:70-117` saves before copying, uses a `tmp-` staging directory and `ATOMIC_MOVE`, excludes root `session.lock`, rejects links/reparse points in scan/copy (`:161-162,179-181,197-198,210-211`), enforces file/byte budgets before copying, checks file count/size/mtime during copy (`:228-235`), and prunes only own-shaped names (`:31-32,120-139`). `PermitService.java:333-343` gives `connect`/`backup` a fresh snapshot on the server thread; `:349-355` enforces the 1,800 s write/PvP freshness boundary. Tests: connect backup, write needs backup, 1800 s boundary, timeout not published, retention, budgets, link in world. Independent junction test: a junction inside the world is refused by `backup` with `link in world`.
- **Restore no-overwrite/protected/source-read-only** — `RestoreTool.java:90-186` requires a new target, a link-free existing parent, no `session.lock` in the source or target ancestors, a matching marker/world id, no overlap with the backup root/source, and treats the source as read-only (copy only, staging + atomic move). Tests: `restoreRules`, `restorePreservesSource`, `restoreRejectsLockedOrRunning`, `restoreRejects`. F4 (64-ancestor bound) and S7/S8 are the remaining gaps.
- **Host shutdown ordering** — `app/pawbot/core.py:562-599` sets `_minecraft_estop` first, then `_minecraft_stop_session` revokes the guard before stopping/cancelling the resident and sidecar; `:454-500` re-checks revoke after stop and computes `sidecar_reaped` from the actual process state. `minecraft_control.py` uses the signed guard revoke as the primary/fallback evidence. F2/F2b are receipt-durability weaknesses, not a missing ordering.
- **Secret/log boundaries** — guard errors are static codes; `PermitService.java:462-464` has no path/secret; `GuardMod.java:216-218` logs static messages; the sidecar env allowlist is `app/pawbot/minecraft_sidecar.py:72-90`; `GuardClient` verifies the signature over raw bytes before JSON (`app/pawbot/minecraft_guard.py:107-127`); Node verifies the signature before reading fields (`app/minecraft-sidecar/src/guard.js:44-53`).

## 6. Test coverage gaps (why the green build does not clear this)

- `cleanupTemp()` is never called by `GuardSelfTest`; `prune` is tested with normal directories only. There is no NTFS junction test at all. The existing `linkInWorld`/`pathSafety` tests use `Files.createSymbolicLink`, which may be unavailable and can silently return from the test; even when available, a symlink is not a junction (`isSymbolicLink` vs `isOther`).
- `revoke` is tested with a writable config directory; no read-only/full/missing directory case.
- `RestoreTool` running-world test covers one level, not >64.

## 8. Recommended order for the lead

1. **Before any live guard use:** fix F1 (junction-following deletion) and add junction regressions for `cleanupTemp`/`prune`. This is the only finding that can destroy the original world automatically.
2. **Before claiming emergency stop is durable:** fix F2/F2b (marker write/verify, signed-receipt durability, kick/port evidence).
3. **Before claiming the resident is viable on a real world:** fix F3/F3b (server-thread backup vs sidecar deadline, single backup interval) and test with a synthetic slow backup >650 ms.

5. **Before final acceptance:** fix F5 (PvP requires write at the guard), F6 (canonical path case policy), and the cross-language config bounds (S11). Treat S1–S13 as residual hardening; do not describe them as live-verified.
6. Re-run the 37-self-test suite plus new junction/revoke-failure/65-deep/pvp-without-write/case tests; then perform the live checklist in §7. A green 37-test log is necessary but not sufficient.

## 9. Bottom line

The guard's core permit/attestation design is credible and the tested paths pass, but the six findings above are concrete correctness/safety defects outside that test surface. F1 is a data-loss bug that defeats the original-world protection; F2 and F3 make emergency stop and periodic backup unreliable; F4–F6 are contract/consistency defects. **Do not represent the guard as live-ready until F1–F3 are fixed and the missing tests are added.**
