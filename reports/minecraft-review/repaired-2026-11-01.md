The source fixes for M1–M5 and S1–S6 are real and the final offline suites are green, including the new F3 snapshot-gate work. Two reproducible gaps remain, plus a stale/moving handoff:

1. **P1 (safety): a non-durable revoke can still be reported as a successful emergency stop.** The guard now returns an unsigned `503` when it cannot persist the revocation marker, but a second revoke (or the host's automatic retry inside one resident stop) gets the sticky `409 revoked`; the Python client maps that to "already revoked", and `core.py` reports `ok=True`. ## 3. Reproducible residual gaps (why the verdict is NOT READY)

### R1 — P1 safety: non-durable revoke can still be reported as a successful stop

**Chain, all reproduced on the final snapshot:**

1. The real guard cannot write the marker (missing config dir): first revoke returns `503 unavailable` unsigned, latches memory, marker absent; a second revoke returns sticky `409 revoked`; a reconstructed service is **not** revoked.
   ```
   first_status=503 signature=false body=unavailable
   first_latched=true
   marker=false
   second_status=409 signature=false body=revoked
   restarted_revoked=false
   ```
   Probe: [RevokeDurabilityProbe.java](reports/minecraft-review/probe/RevokeDurabilityProbe.java), log [probe-revoke-durability-java-final.log](reports/minecraft-review/repaired/probe-revoke-durability-java-final.log).
2. The real Python client maps `409 revoked` to `GuardAlreadyRevoked` ([minecraft_guard.py](app/pawbot/minecraft_guard.py#L260-L274)), and `core.py` treats that as `revoked=True` ([core.py](app/pawbot/core.py#L446-L464)). `_minecraft_stop_session` retries the revoke after stopping the resident ([core.py](app/pawbot/core.py#L504-L511)), so **one** resident emergency stop turns the 503 into a 409 success.
3. The real `Bot.minecraft_emergency_stop` then reports `ok=True` although no durable marker exists:
   ```
   resident_single_call = {"ok": true, "revoked": true,
     "revoke_receipt": "already_revoked", "resident_stopped": true, ...}
   FALSE_SUCCESS: one resident stop reports ok without a durable revoke
   ```
   Probe: [revoke_durability_false_success.py](reports/minecraft-review/probe/revoke_durability_false_success.py), log [probe-revoke-durability-final2.log](reports/minecraft-review/repaired/probe-revoke-durability-final2.log). The no-resident path has the same issue on a **second** stop call (first `ok=False`, second `ok=True` with `already_revoked`).
4. Impact: an operator/CLI can be told the emergency stop succeeded, but a process restart re-arms the guard. This contradicts the protocol §4 "ok: true requires every step confirmed" and the guard's own `revokeMarkerWriteFailure` documented consequence.

**Fix direction:** make the guard distinguish "in-memory latched but not durable" from "durable already revoked": e.g. keep returning `503` (or a distinct unsigned code) while the marker is absent, or add an explicit `durable`/receipt field and make clients refuse `ok` without it. On the host side, do not treat `GuardAlreadyRevoked` as proof of durability; only a signed receipt or a verified durable marker may set `revoked=true`. Add a regression that calls revoke twice against a missing config dir and asserts both calls fail (or that `ok` stays false), and a core test with a 503→409 sequence.

**Test gap:** `revokeMarkerWriteFailure` asserts only the first revoke and the restart; it never calls revoke a second time. The host tests use a fake guard that raises `GuardAlreadyRevoked` directly, so they encode the unsafe equivalence rather than catching it.

### R2 — P2 functional: the farm "no plantable soil → shelter" fallback is unreachable

`_farm_soil` returns a fallback `{"x":..., "y": fy-1, "z":..., "block": "unknown"}` whenever `fy-1` is inside the world, even when the observation contains no soil ([minecraft_resident.py](app/pawbot/minecraft_resident.py#L2994-L2999)). `_ensure_project` only falls back to shelter when `_project_steps` returns an empty list ([minecraft_resident.py](app/pawbot/minecraft_resident.py#L2928-L2933)), so it keeps a farm project on stone/gravel/air and the child rejects `not_soil`.

Reproduced with only stone under the player:
```
kind = farm
steps = [move(2,64,2), farm(0,63,0,seed=wheat_seeds), eat]
FARM_ON_UNPLANTABLE_GROUND: project kept a farm step instead of falling back to shelter
```
Probe: [farm_fallback_probe.py](reports/minecraft-review/probe/farm_fallback_probe.py), log [probe-farm-fallback.log](reports/minecraft-review/repaired/probe-farm-fallback.log). The existing test `test_immature_crop_is_skipped_and_bad_soil_is_not_claimed_as_success` calls `_project_steps` directly and asserts the child rejects the fallback; it does not assert the claimed shelter fallback. Fix: return `[]` when no observed soil matches; only emit `y-1` if that exact block is observed as farmland/dirt/grass. Add an `_ensure_project` test that barren ground produces a shelter project (or no farm).

### R3 — P2 functional: generated farm soil can be outside the child's 4.5-block reach

`_farm_soil` selects up to two soils within 2 blocks of the **feet**, but the single `move` step chooses a stand cell without checking distance from the selected soils ([minecraft_resident.py](app/pawbot/minecraft_resident.py#L3023-L3043)). With soils at `(2,63,2)` and `(-2,63,-2)`, the chosen stand is `(2,64,0)`:
```
stand=2.0,64.0,0.0 soil=-2,63,-2 distance=4.583 child_limit=4.5 ok=False
OUT_OF_REACH: farthest generated farm is 4.583 > 4.5
```
Probe: [farm_stand_reach_probe.py](reports/minecraft-review/probe/farm_stand_reach_probe.py), log [probe-farm-reach-final2.log](reports/minecraft-review/repaired/probe-farm-reach-final2.log). The real Node adapter checks `within 4.5` at the moment of the farm call ([adapter.js](app/minecraft-sidecar/src/adapter.js#L128-L129), [adapter.js](app/minecraft-sidecar/src/adapter.js#L238-L254)); the contract fake rejects the same case. A `GoalNear(radius=1)` may stop closer than the commanded point, but the generated sequence does not guarantee the child's reach, and no test covers opposite-corner soils. Fix: filter soils by the chosen stand's reach (with margin), choose a stand minimizing max distance, or emit move+farm per soil. Add a cross-contract test with opposite-corner soil.

### R4 — P3 consistency: resident owner conflict rule differs from the host helper

`_owner_human_uuid` rejects only "equals the bot actor" ([minecraft_resident.py](app/pawbot/minecraft_resident.py#L1574-L1589)); it does not call the host `owner_human_identity` that also rejects `owner_mappings` conflicts ([minecraft_policy.py](app/pawbot/minecraft_policy.py#L53-L97)).
