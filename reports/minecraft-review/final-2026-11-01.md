## 2. Must-fix findings

### M1 (BLOCKING, security) — a permit can be issued after `revoke` has completed

`PermitService.handle` checks `revoked` before submitting the server-thread task (`minecraft-guard/src/main/java/dev/pawbot/guard/PermitService.java:211-214`, then again at `:257-259`) and submits `build` at `:287`. `build` (`:301-361`) never re-checks `revoked` or the marker, while `revoke` sets `revoked = true` at `:392` on another HTTP thread. A request that passed the check but is waiting for the integrated-server thread therefore receives a fully signed 200 response **after** revocation.

Reproduction (saved probe, run against the built classes):

```powershell
$javac='C:\Program Files\JetBrains\PyCharm 2025.2.4\jbr\bin\javac.exe'
$java ='C:\Program Files\JetBrains\PyCharm 2025.2.4\jbr\bin\java.exe'
& $javac --release 17 -encoding UTF-8 `
  -cp 'minecraft-guard\build\classes\java\main;minecraft-guard\build\classes\java\test' `
  -d $env:TEMP\pawbot-race reports\minecraft-review\probe\RevokeRaceProbe.java
& $java -cp "$env:TEMP\pawbot-race;minecraft-guard\build\classes\java\main;minecraft-guard\build\classes\java\test" `
  dev.pawbot.guard.RevokeRaceProbe
```

Observed:

```text
revoke_status=200 isRevoked=true
connect_after_revoke_status=200
connect_after_revoke_body={... "action":"connect" ... "backup_id":"backup-..." ...}
```

Impact: violates `docs/MINECRAFT-PROTOCOL.md` ("Revoke disables subsequent permits/actions") and the emergency-stop promise. A queued **connect** permit (with a fresh backup id) is issued after revocation, so a sidecar could reconnect and proceed. **Owner: Fabric/guard author.** Fix by re-checking revocation inside `build` immediately before signing and serializing revoke/publication (lock or generation counter); do not publish a new `sessionBackup` after revocation. Add a concurrent revoke-vs-permit regression.

### M2 (BLOCKING, safety) — no-resident emergency stop reports success without confirming revoke

`core.py:543-551` treats **any** `GuardDenied` whose text is `invalid_guard_settings` as "本机根本未配置守卫" and sets `ok=True`, `revoke_skipped="not_configured"`. But `invalid_guard_settings` also covers a configured guard with the default/stale LAN `port=0`, bad world path, bad actor UUID or bad URL (`minecraft_guard.py:49-73`). The no-resident branch (`core.py:530-551`) therefore returns success with `revoked=False` when a secret is configured but the local settings are invalid. `minecraft_control.stop_via_control` (`minecraft_control.py:84-88`) additionally accepts `session=="none"` without requiring `revoked`, so the CLI can report success too.

Reproduction (saved probe):

```powershell
py -3.13 reports\minecraft-review\probe\emergency_stop_false_success.py
```

Observed with `PAWBOT_MC_GUARD_SECRET` set to a 40-character test value, `minecraft.port=0`, and no resident:

```text
{'ok': True, 'latched': True, 'revoked': False, ... 'session': 'none',
 'revoke_error': 'GuardDenied', 'revoke_skipped': 'not_configured'}
```

Impact: an operator or CLI sees a successful emergency stop although no guard revocation was confirmed. This is exactly the default `port=0`/stale-port state. **Owner: integration/core author.** Only skip revocation when no guard credentials are configured at all (e.g. empty `PAWBOT_MC_GUARD_SECRET`), not for every invalid-settings reason; otherwise return `ok=False` with `invalid_guard_settings`. Add tests for secret-present + port 0/bad path/bad actor and for a control result with `session=="none"` + `revoked=False`. Consider treating a `409 already revoked` as already-safe rather than a failure.

### M3 (BLOCKING, functional) — every `home` skill fails because the resident never seeds the sidecar's `set_home`

Node's adapter stores home only in process memory: `home` requires `this.home` and `set_home` sets it (`app/minecraft-sidecar/src/adapter.js:244-245`); the sidecar README says `set_home` is process-only (`README.md:90-91`). The resident never emits `set_home`: it appears only in the schema and model-affordance lists (`app/pawbot/minecraft_resident.py:397,1798`), never in `SKILLS`/`_select_skill` (`:59-68`, `:1875-1890`) or `_project_steps`. The resident's persisted `_home()` (`:1990-1994`) is only a local place, never sent to Node. Every `home` the resident generates (rest, recover, explore-project completion, default promise steps, low-energy drive) therefore raises `GameError` in Node and is recorded as a resident failure; after a sidecar restart even a previously set in-process home is lost.

Impact: "回家"/rest/recover/explore project completion and default promises fail in a real world; the acceptance item "下雨回家/睡前写日记" cannot be demonstrated. **Owner: resident/integration author.** Send `set_home` after the first verified observation and after every reconnect (or add an explicit persisted home-coordinate skill); include `set_home` in an intent allow-list and align the controller's action classification (it currently treats `set_home` as write, while the adapter uses an observe permit). Add a resident contract test with a fake sidecar that rejects `home` until `set_home` is sent.

### M4 (BLOCKING, functional) — farm project uses the player's feet as the soil coordinate

The farm project generates `farm` at the anchor `y` (`minecraft_resident.py:2299-2308`), where `anchor` is the player position (`:2281-2284`). Node's `farm` expects the **soil block** at `(x,y,z)` to be `farmland`/`dirt`/`grass_block` and the crop at `y+1` (`app/minecraft-sidecar/src/adapter.js:195-211`). At the player's feet the block is normally air, so the skill raises `GameError`; the project pauses after repeated failures. The synthetic 60-minute test uses a fake sidecar that accepts every skill, so it does not catch this.

Impact: the required farm/agriculture route fails in a real world. **Owner: resident author.** Use `y-1` or a loaded ground/farmland coordinate derived from the observation; add a cross-contract test that passes the generated args through the real Node schema/behavior.

## 3. Blocking spec/acceptance gap (product decision)

### M5 — no owner-human identity or owner-specific behavior

`_context` hardcodes `"owner_present": False` (`minecraft_resident.py:1813`); `_update_social` only assigns `role` `self` for the bot actor and `player` for everyone else (`:2188-2197`); `owner_mappings` produces only a boolean `explicit_link` (`:1356-1370`). The config binds the bot actor UUID to `owner_qq_uid` (format-validated), but there is no owner-human Minecraft UUID and no owner role/attitude. This matches the resident author's own interface finding ("owner_player_uuid is the bot actor UUID, not the owner human's avatar ... owner_present false absent a separate owner-human UUID source").

The v4 acceptance criterion "她能区分主人与其他玩家，对不同关系表现不同态度并记得共同经历" cannot be demonstrated as written. **Decision needed from the lead/owner:** either add an explicit `minecraft.owner_human_uuid` (and owner role/behavior/tests), or narrow the documented acceptance to "owner = QQ owner; all in-game players are separate social models". The protocol's statement that the bot actor is not the owner avatar is intentional, so this is a product/design gap, not a byte-level safety defect.

## 4. Should-fix cross-contract and robustness findings

### S1 — revoke receipt with `port:0` is rejected by both clients

The guard's `revoke` path returns `world.lanPort()` (`PermitService.java:394-403`), which is 0 when LAN is closed. A probe with `FakeWorld.port=0` produced a signed 200 body containing `"port":0`. Python `verify_attestation` requires `row["port"] == settings.port` (`minecraft_guard.py:125-128`); Node requires `p.port` 1..65535 (`app/minecraft-sidecar/src/guard.js:51`). A successful revocation can therefore be reported as verification failure (false negative) when LAN is closed, though the guard did revoke. Consider accepting `port=0` specifically for `revoke` (or define a revoke-specific field) while keeping all action permits strict. Owner: guard + both clients.

### S2 — no-resident direct revoke ignores `minecraft.guard_url`

`core.py:430-431` reads only `PAWBOT_MC_GUARD_URL` (default port 6198); the resident does use the configured `minecraft.guard_url` (`minecraft_resident.py:1285-1287`). If the operator sets only the config key, ordinary resident permits work but the no-resident/CLI fallback targets the wrong endpoint. Use the config value as fallback, with env override, in both paths. Owner: integration/core.

### S3 — Windows path case is accepted by settings validation but rejected by exact attestation

`GuardSettings.validate` compares `normcase(realpath(world_path))` (`minecraft_guard.py:70`), so an uppercase spelling of an existing path validates. The guard signs `toRealPath()` (`PermitService.java:412-417`), and the client compares exact strings (`minecraft_guard.py:138-140`; Node `guard.js:51`). Reproduced: `settings_validate=PASS`, then `attestation=DENIED guard_world_mismatch` for a correctly signed row using the actual case. This is fail-closed but means a normal Windows spelling mistake produces every-permit failures instead of a clear config rejection. Require the exact canonical spelling in settings validation, or compare canonical forms consistently. Owner: integration/guard.

### S4 — `RestoreTool` atomic-move overwrite race (low)

`RestoreTool` checks the target does not exist (`:118`), copies into `<target>.restoring`, then `Files.move(..., ATOMIC_MOVE)` (`:178`). An existing target created between the check and the move may be replaced on POSIX implementations. Use a non-replacing move or re-check/lock immediately before publication. Owner: guard/restore.

### S5 — config bound mismatches across layers

`world_id` is 1–128 in Python/Node but 1–64 in Java (`GuardConfig.java:38`); `secret` is 32–4096 in clients but 32–256 in Java (`:80`); Node accepts up to 64 PvP targets while Java accepts 16 (`:93`); Python does not cap the PvP list. These are fail-closed at config load but can reject a config that the clients accepted. Document the guard's stricter bounds and/or align validation.

### S6 — observation breadth gaps

Node `observe` emits health/food/position/dimension/inventory/entities/blocks (`adapter.js:251-258`) but no `time_of_day`, `weather` or safe events. The resident accepts `time_of_day`/`weather` if present (`minecraft_resident.py:315-323`), and v4 §4.7 asks for weather/time/light/roof to influence affect and habits; currently rest habits use wall-clock `time.localtime`, not game time. This is a feature-completeness gap, not a safety bug. Also the resident's intent allow-lists contain no `attack`, so the guard/policy/Node PvP skill is unreachable from autonomous behavior (PvP remains default-off).

- **Guard authorization order**: constant-time bearer check, exact content type, bounded body, exact request key set, 32-lowercase-hex nonce, actor equality, PvP exact target list, write/PvP flags, nonce claimed before decisions, revoke marker checked per authenticated request and at startup, 5-second signed lifetime, exact raw-byte HMAC, no unsigned success bodies, no world paths in unauthenticated errors.

- **Sidecar**: real HMAC before JSON parse; exact nonce/action/actor/target/world/path/host/port/lifetime checks; backup before connect and fresh connect permit immediately before the socket; actor UUID after spawn; schema-only skills; no eval/exec/RCON/filesystem/raw commands; pathfinder restrictions; PvP target/type checks; cancellation/quarantine/no mutation replay; child env allowlist; auth CLI only interactive TTY and protocol never requests a device code.
- **Resident**: bounded 3–5 workspace; shared `bot.persona`/`bot.emotion`/`bot.longmem`; drives/residue/decay; projects/promises/places/players/journal; intent-only model output; budget reservation before remote calls and no refund; failure/repeat handling; bounded reconnect; estop latch; no private-thought/QQ-UID/path persistence in the checked state/diary/model context.
- **Host**: relay mode returns before `_start_minecraft_resident`; sidecar/resident failures are contained away from QQ; emergency-stop order is revoke → cancel/stop → reap; normal shutdown latches and drains; control route requires loopback peer + independent bearer token; hostile/oversized bodies rejected.
